HomeSet agent architecture (version 5, as built)

One request: message in, plan out. Code decides before the model is called and again after it writes; the model writes the plan in between. Blue = new since version 4 (the health question, 2026-10-19). Red marks where prompt injection gets in and where the design is weakest. Valerie Zandoli and Yadan Taino. Drawn from the code at commit cef5ee2. This replaces version 4, which did not show the health question.

1USER MESSAGE

minutes, equipment, and focus area, in one sentence. In a swap session: the request to change one exercise.

Where it comes from: the command line (python -m homeset) or the chat page (python -m homeset.web, this computer only).

WHERE THE HEALTH QUESTION IS ANSWERED

  • Command line: you answer at a terminal, up to two tries. With no terminal it prints the question and stops; --no-health-issues says in the command that there is none.
  • Chat page: a "None of these" button, or type. A reloaded page is a new conversation.

3SAVED PLAN FILE

saved_plan.json: one plan and its time stamp; no symptoms, no request text. Owner-only, kept out of git.

On load it is ignored if it is a link, belongs to another user, can be changed by others, is over 32 KB, or is not a valid plan.

SAVE CHECKPOINT

The model has no tool for the write. A person types the exact answer "yes" at a terminal, or clicks "Yes, save" on the chat page. Anything else, or no terminal, saves nothing.

It shows the saved plan beside the new one and asks once. The approval covers one exact text; the write is atomic.

TO THE USER

a plan, only after every output check passes;
or, with no plan: the hand-off sentence, a fixed question, or an error message.

REQUEST TRACE

Each step is recorded in order: the safety check, the health question, every model call, every tool call, the "(assumed)" change, every check, and the outcome. --trace prints it.

HARNESS (the code that runs the loop)

SAFETY CHECKS IN CODE (run first; the model is not called when one fires)

  1. Health words (pain, injury, surgery, pregnancy, a medical condition) anywhere in the conversation: the exact hand-off sentence goes to the user. A negated word ("no pain") does not fire.
  2. Vague wording ("feels off", "bothering me"): one fixed question, "Is that ordinary soreness or tiredness, or does it hurt?" A second vague message: the hand-off.
  3. NEW — the health question, before the first plan: "Before I plan: do you have any pain, injury, surgery, pregnancy, or medical condition I should know about? Reply "none" or tell me." Only a short list of exact answers ("none", "no", "no pain", ...) lets the request go on. A health word in the answer: the hand-off. An unclear answer: asked once more, then the hand-off.
  4. Skips the question: a request that says "no pain" or "no injuries"; a swap of a saved plan from the last 7 days; a user who answered the vague question.

Anything else goes on to the model.

MODEL + SYSTEM PROMPT

Decides:

  1. focus and equipment labels, from the fixed lists
  2. which exercises, from the tool results only
  3. sets, reps, and rest; writes the plan
  4. the fixed messages for missing minutes, no match, too few exercises, or wger down

Prompt step 1 stays as a second layer for health wording that neither code list knows: a body part or symptom the user calls fine is not a symptom. In a swap session it receives the saved plan once, as data.

OUTPUT CHECKS IN CODE (plans only, before the user sees it)

  1. The format is exact (line 1, numbered lines, total line).
  2. The last line is the exact safety line.
  3. Every exercise name came back in this request's results.
  4. The user owns all the equipment: the wger tag and the gear the name implies (bodyweight is always allowed).
  5. No blocked advanced move (pull-ups, plank-to-row).
  6. No kettlebell move above 8 reps per set.
  7. The stated total matches the code's own sum.
  8. The total is within 5 minutes of the request.

One failed check sends the plan back to the model once; a second failure shows a visible error and no plan.

homeset/checks.py · gear.py · advanced.py · rep_cap.py

TOOL RUNNER (code)

The model has two tools and no others: search_exercises(focus, equipment) and calculate_plan_time(exercises).

Cap: 10 tool calls per request; a refused call counts. Argument caps: a list of at most 20 items; an equipment string of at most 60 characters.

Labels are checked against the fixed lists and turned into wger filters by code. An unknown label is an error, and no search runs.

wger: GET only, 10 s timeout, 1 retry, 30 s at most per search.

2wger EXERCISE API

read-only; names and text can be edited by strangers. One search per muscle in the focus label, five at most.

CONTEXT FEEDING (code)

Builds one clean record per exercise: English name, equipment, muscles, category, and the ids that the checks use. Drops every other field, including descriptions.

Drops a name that is not a short label (the injection filter), an advanced move, a repeat, and any exercise that needs gear the user lacks. Marks a cut list: "showing N of M".

homeset/wger.py · gear.py · advanced.py

TRUNCATION POINT

wger returns 20 exercises per page. Code follows the next-page link up to 40 rows for each muscle and marks any cut, so the model can see that the list is partial.

Still open: rows past 40 are never seen, so a cut list can hide better exercises.

THE LOOP STOPS WHEN

  1. A plan passes every output check.
  2. A health word is found: the hand-off sentence, and the model is not called.
  3. Vague wording: the one fixed question, and the model is not called. A second vague message: the hand-off.
  4. The health question is unanswered or unclear twice: the hand-off.
  5. The regenerated plan fails a check: a visible error message, and no plan.
  6. The model asks for an 11th tool call: a visible message, and no plan.
  7. The model writes one of its fixed messages: the harness passes it on without the output checks.

THE LOOPS (letters in the flow)

A Replan: the prompt asks the model to land within 2 minutes of the request. If calculate_plan_time shows more, the model changes the plan and calls the tools again, up to 2 more times. Only the prompt asks for this; code only caps the request at 10 tool calls.

B Failed output check: code sends the list of failed checks back to the model once. Code writes the "(assumed)" marker again on the new plan.

C Save and swap, in a later session: after a plan, a "yes" saves it. A later swap run loads the file and gives it to the model once, as data, with the swap request. The same safety checks and output checks apply.

D Code-fired questions: the vague question and the health question are asked by code. The answer goes to the model together with the earlier request, after the safety check reads the answer first.

HOW TO READ THIS

1, 2, 3 Where prompt injection gets in:

1 the user message (and the answer to a question); 2 wger text; 3 the saved plan file (a swap session).

Harness catches:

health words before the model; an unclear health answer; labels off the fixed lists; invented names; gear the user lacks; advanced moves; kettlebell reps over 8; a wrong total; oversized tool arguments; tool failure.

Harness does not catch:

intent in the message (the prompt carries it); injected words inside a plausible exercise name; an injury in wording neither list knows (only prompt step 1 stands there); a false "none" (the answer is self-reported); a model reply that is not a plan (it skips the output checks).
