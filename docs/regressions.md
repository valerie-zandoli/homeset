## Where the failure guards can still be silent (2026-10-14)

1. **A tiny page.**  The unreadable-name guard needs 5 or more results.  A page of 4 or fewer results that are all unreadable still reads as "no exercises".  Live pages never had fewer than 25 examined per focus label, so the risk is low; the canary would show a collapse.
2. **A plausible but wrong record.**  A record with a readable name and a wrong muscle or equipment tag passes every check (the name-based gear check in `homeset/gear.py` covers one case).  Find out by a monthly spot check:  compare 10 sampled exercise IDs with the wger website page.
3. **A frozen or cached copy of wger.**  A stale answer looks healthy.  The canary's floors catch a collapse in size, not staleness.  Find out by comparing the exercise count and one recently edited entry with the website before the demo.
4. **Legitimately small answers.**  A thin result (few exercises for a focus with little gear) is a real answer and ends in the "found only <n>" question, not an error.  The canary uses floors set at half of the 2026-10-14 live count, so it tells a thin answer from a broken one for the 12 focus labels with a mat and dumbbells only.
5. **Owner.**  The saved `tool_errors` list and the canary exit code have no reader unless someone runs them.  Owner:  whoever runs the pre-demo checks (Valerie and Yadan); run the canary right after the text scan.

## Known gap, not fixed

`equipment` and `muscles` names are passed to the model exactly as wger sends them.  They come from small admin-curated tables, not community edits, so the risk is low.  The stronger fix is to show the model our own label for each ID.  Revisit if wger lets users edit those tables.
